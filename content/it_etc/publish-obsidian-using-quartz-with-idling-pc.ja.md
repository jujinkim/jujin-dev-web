## 概要
Obsidianをウェブに公開する方法は様々ありますが、最も簡単な方法は、Obsidian Publishを月額8ドルで使用することです。この方法はワンクリックで記事を公開でき、カスタムドメインもDNS設定一つで全て自動的に行われるため、非常に便利という利点があります。しかし、カスタマイズが制限され、月額8ドルという金額は安くありません。私はObsidian Sync（4ドル）を使用していますが（カスタム同期は不安定だと考えています）、これにわざわざ8ドルを追加で使いたくありませんでした。

この記事では、私が使用した方法を共有しようと思います。Obsidian Syncは使用しても使用しなくても構いませんが、公開用のコンピュータ（ホームサーバーであればなお良い）が1台必要です。サイト自体はGitHub Pagesを使用して公開するため、ホームサーバーが24時間稼働している必要はありませんが、記事を書くたびにホームサーバーを起動するという手間があるでしょう。個人PCでもスクリプトを実行するだけで済むので問題ありません。

このブログは、Obsidian + Sync、Quartz、そして常に電源が入っているPC（遊んでいるPC）を組み合わせて構築およびデプロイが自動化されています。
どこからでもObsidianで記事を作成して同期すると、別のPCで自動的にビルドおよびデプロイプロセスが実行される仕組みです。
これにより、ユーザーは記事作成だけに集中できます。

## 記事作成と同期: ObsidianとObsidian Sync
全ての記事はObsidianで作成され、自動的にMarkdown形式で保存されます。
PC、モバイルなど、Obsidianクライアントがサポートするあらゆるデバイスで記事を作成または編集できます。

Obsidianの公式有料サービスであるObsidian Syncを使用して、全てのデバイスのノートがリアルタイムで同期されます。この際、GitHub Pagesに記事をアップロードする用途であるホームサーバーにもノートが同期されます。
これがこのシステムの核心であり、ローカルファイルではなくObsidianサーバーを単一真実供給源（Single Source of Truth）として使用します。もしObsidianをPCでしか使用しない場合、PCのObsidian VaultがSSOTとなります。

Obsidian Syncを使用しなくても構築自体は可能です。Gitなどで自己同期を行うか、個人PCでのみ使用するかに関わらず、公開するフォルダを選択してGitHubにアップロードする部分だけを自動化すれば良いためです。

## 自動ビルド環境: 遊んでいるPC
家に常に電源が入っているPC（ホームサーバーまたはデスクトップ）がこの役割を担います。ホームサーバーがない場合は、個人PCでも構築可能です。
このPCにもObsidianアプリがインストールされており、同じObsidianアカウントでログインしてノートを同期します。

ホームサーバーにはLinuxをインストールしましたが、ここで`inotify-tools`を使用してObsidian Vaultディレクトリのファイル変更をリアルタイムで検知します。
ファイル変更が検知されると、自動的にビルドおよびデプロイプロセスを開始します。
自動デプロイが不要な場合はこの部分はスキップしても問題ありませんが、その場合はPCで以下のデプロイを手動で実行する必要があります。

## ビルドとデプロイの自動化: Quartzとシェルスクリプト
まず、デプロイのためにはObsidian Vaultではなく、別の新しいプロジェクトフォルダを作成する必要があります。Obsidian Vaultには触れず、全てのデプロイ作業はプロジェクトフォルダで行われます。

`Quartz`は静的ウェブサイトビルダーの一つで、Obsidianを公開することに最適化されたプログラムです。グラフも描画でき、ローカルでのビルドも可能です。

Obsidian Vault内のデプロイ対象フォルダのファイル変更が検知された場合、以下の動作を実行します。

*   **コンテンツ同期**: Obsidian Vaultの最新コンテンツをプロジェクトの`content`ディレクトリにコピー（`rsync`）。
*   **サイトビルド**: Quartz CLI（`npx quartz build`）を使用してMarkdownファイルを静的ウェブサイトファイルに変換し、`public`ディレクトリにビルド。
*   **Gitプッシュ**: 変更がある場合、Gitを使用して自動的にコミットし、リモートリポジトリ（GitHub）にプッシュ。

Obsidianの記事を直接触らず、デプロイ用フォルダにコピーした後、このフォルダ内のコンテンツを加工してデプロイするため、既存の記事は安全です。また、Obsidian Vault全体をデプロイするのではなく、デプロイ用フォルダを選択できます。そのフォルダのみがデプロイ用フォルダとしてデプロイされるためです。

ここで言う「フォルダ内のコンテンツ加工」とは、コピー後にコンテンツに自動で情報を追加したり、翻訳コピーを別途生成したりすることを意味します。このサイトの場合、コピー後に自動で3カ国語の`Gemini`が翻訳コピーを生成します。コピー後に生成されるため、既存のObsidian Vaultには不要な翻訳版が表示されず、実際にファイルを「生成」してからデプロイするため、その言語でも外部から検索できるようになります。

## 最終デプロイ: GitHub Pagesおよびカスタムドメイン接続
メインブランチに新しいコミットがプッシュされると、事前に設定されたGitHub Actionsワークフローがトリガーされます。
このワークフローは`public`ディレクトリの静的ファイルをGitHub Pagesにデプロイします。

必要に応じてビルドをPC（サーバー）ではなくGitHub Pagesで行うこともできますが、この場合、ビルドに時間がかかり、ローカルでウェブサイトをテストするのが面倒になります。そのため、私はPC（サーバー）で事前にビルドを行い、完成したページのみをアップロードすることを選択しました。

### GitHub Pages設定
実際のデプロイはGitHub -> GitHub Pagesを通じて公開されます。そのため、Pagesの設定も必要です。
GitHubリポジトリ設定の「Pages」セクションでGitHub Pagesを設定できます。
「Source」を「Deploy from a branch」に設定し、「Branch」を`gh-pages`（または`main`ブランチの`docs`フォルダ）を選択した後、`/(root)`フォルダを選択します。
保存するとGitHub Pagesが有効になります。

もしご自身で購入したCustom domainがあれば、一緒に[設定](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages)してください。

## 結論
このシステムにより、ユーザーは記事作成だけに集中できるようになります。Obsidianに記事を書いて保存するだけで、複雑なビルドおよびデプロイプロセスが自動的に処理されます。
Obsidian Syncを中央ハブとして使用し、遊んでいるPCを自動化エージェントとして活用するのが、この構造の核心的なアイデアです。遊んでいるPCがない場合でも、ご自身のPCでデプロイスクリプトを一度実行するだけで自動的に「`Obsidian Vault` -> `Copy to Content directory` -> `Process contents` -> `Upload(push)` -> `Publish`」が実行されます。

## 追加
この全てのプロセスを直接コーディングしたわけではなく、`Codex`、`Claude Code`、`Gemini`の助けを借りて開発しました。
個人的にGeminiはまだローカルでのコーディング作業をプロジェクト単位で指示するには適していないと感じているため、翻訳用途のみで使用しています（3.0モデルに期待しています）。CodexやCCに現在の環境（ホームサーバーの有無など）と上記の要点をまとめてサイトを構築するよう依頼すれば、うまくやってくれるでしょう。そのため、本文にはスクリプトコードなどは含んでいません。アイデアを共有しましたので、ご自身の環境に合わせてうまく調整してください。
